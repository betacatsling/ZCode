# ACP HarnessAdapter v2 (bounded target-local seam)

ACP is a harness-managed model route only; neither ACP nor a native model ID authorizes ZCode model injection. A trusted factory supplies an immutable manifest and pinned absolute executable/argv/isolated env/exact version plus a target-owned `verifyCwd(spec)` returning the canonical worktree-contained cwd. The adapter compares the verified cwd with the descriptor cwd and rejects mismatched identities, generations, versions or target IDs. No repository manifest executes code, no discovery starts a process, and an unavailable version is unsupported with an explicit reason. Version availability alone is experimental; `certified` is an explicitly trusted profile assertion only after native prompt/tool/permission proof for the exact pinned binary. It must not be set from a synthetic test or agent-advertised capabilities. Two separately configured profiles may share this factory without sharing a process.

The Host remains the sole owner of command admission, durable receipts and event journal. The adapter owns one ACP process per attached session, native ID, epoch, active turn, pending permission correlation and per-session sequence. `create` opens exactly one native session. `attach` opens a fresh process only after negotiated `loadSession === true`; absent load is **history-only** and cannot start another native session pretending to resume. Native ID is not a Host ID. Detach only removes a subscriber in the Host; `shutdown` is target process shutdown and may interrupt running work. Explicit terminate closes only that session. A process exit during a turn is an unknown execution result, never retry the prompt. The Host must durably accept approval/denial before calling `resolveInteraction`; adapter verifies epoch, turn and interaction again. Native permission request holds the ACP response until that command, cancellation/exit denies it, and late decisions fail. FS/terminal client requests must be independently Host-authorized callbacks; no default capabilities advertised.

```text
Host verified spec + durable create -> adapter descriptor/version probe -> ACP initialize -> session/new -> binding(epoch,native ID)
Host frozen harness-managed turn + durable send -> ACP prompt -> validated update -> canonical(seq,epoch,turn) -> Host journal
ACP permission -> interaction.requested -> Host durable decision -> adapter resolve -> ACP selected/cancelled -> interaction.resolved
Host cancel(epoch,turn) -> deny pending permissions -> ACP cancel -> turn.finished(cancelled); late reply/decision never starts a new turn
Host attach(binding) -> verified cwd + initialize + negotiated loadSession -> session/load(native ID) or fail history-only
```

Only known structured ACP updates map to canonical text, reasoning (inert extension), tool start/update/end, plan, usage and status. Unknown extensions are inert. Message deltas and final messages share stable per-turn IDs; no text completion inferred from stdout. `session/prompt.stopReason` is the authoritative turn completion. Non-cancelled errors fail closed, not successful. ACP updates with wrong native session or no current turn are ignored. No replay of an admitted turn on reconnect; a new epoch after load rejects stale commands and approvals. This adapter is target-local: SSH requires a separately trusted target-local executable/verification service, not a local path masquerading as SSH.

Acceptance: two independently trusted manifest+factory profiles; wrong executable/version/cwd/route rejected; two sessions isolated; native negotiated load vs history-only; held pre-tool permission, cancellation and late stale approval; canonical update projection, no shared process overkill. Pinned public `@zed-industries/claude-code-acp@0.16.2` was run in an isolated HOME with loopback-only provider URL for **initialize only**; it advertised protocol v1 and loadSession. Its entrypoint has no `--version` command (it starts stdio); a trusted package-version/hash probe is required at composition instead of CLI `--version`. Its native `createSession` defaults to SDK `settingSources=[user,project,local]`; project/local settings or tools must be isolated/disabled and a fake loopback upstream must prove prompt, pre-tool denial and real load before this profile is certified. The second profile is synthetic only; no second independently available binary was verified. No live account, paid call or product certification from component tests.

## Pinned Claude ACP certification boundary (2026-09-24)

The target-local composition verifies the **installed** 0.16.2 package identity and executable byte digests before any process launch; `--version` is not a probe. A pinned profile is never certified merely because initialize advertises load: native new/prompt, actual pre-tool deny/cancel, and load must be exercised with a loopback fake provider and isolated HOME/key. The second manifest-only synthetic agent tests adapter reuse, not two independently certified agents. The ACP adapter owns process-local pending permissions, not provider credential or persistent admission.

Crucial source finding: in 0.16.2 `createSession` constructs `SettingsManager(params.cwd)` and initializes it **before** SDK `query`; independently reads `.claude/settings.json` and `.claude/settings.local.json` from the workspace. SDK query defaults `settingSources=[user,project,local]`; even if the client supplies `_meta.claudeCode.options.settingSources=[]`, the ACP SettingsManager hook still loads project/local rules and may return `permissionDecision: allow` before `canUseTool` gets a vote. Thus real native loopback denial in a clean temp worktree is not proof that arbitrary repository settings cannot bypass approval. Until target isolation or upstream fix is source-proven across hooks and project settings, approvals/tools for this profile stay **experimental/unsupported**; even an incorrectly configured `certified: true` must not promote a pinned Claude package descriptor to supported. Admission with a forged supported plan must fail closed, independently of probing; generic synthetic profiles remain distinct. No settings in actual user HOME or global account are modified.

Event sequence: Host durable admission -> target verifies worktree generation/cwd -> digest probe -> native process initialize/new -> prompt -> ACP request_permission (if reached) -> Host durable decision -> one ACP reply -> prompt completion. Cancel invalidates the pending decision; native prompt settlement is required before the next turn; reconnect uses native ID and negotiated load only. No synthetic receipt is counted as native execution.
