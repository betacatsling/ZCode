# Codex app-server adapter scope

The adapter slice pins CLI 0.157.1 and communicates using its JSON-RPC app-server over stdio, not TUI scraping. The 0.156.1 note below is historical probe evidence only. At create, use an isolated `CODEX_HOME` and a session-scoped custom `model_provider` pointing only at the target-local Gateway; do not write global `~/.codex/config.toml` or pass credentials in command arguments. `thread/start`, `turn/start`, `turn/interrupt`, `thread/resume`, item and turn notifications, usage, and server-initiated command/file approval are distinct control surfaces. An approval callback must retain the exact RPC request ID until the target host durably accepts the matching response. Unrecognized requests never auto-approve. The adapter version and CLI version must match; an upgrade returns history-only until fixture revalidation. See [Codex HarnessAdapter spec](CODEX-HARNESS-ADAPTER.md) for the new adapter contract.

On 2026-09-24, an isolated `codex-cli 0.156.1` probe (`ZCODE_CODEX_PROBE=1 node packages/services/test/fixtures/probeCodexAppServer.mjs`) completed initialize → thread/start → turn/start, then sent `POST /v1/responses` with `client_metadata`, `include`, `input`, `instructions`, `model`, `parallel_tool_calls`, `prompt_cache_key`, `reasoning`, `store`, `stream`, `tool_choice`, `tools` and `stream:true`. By default the fake Gateway intentionally replied 400, yielding a structured `error` notification. With `ZCODE_CODEX_PROBE_FAKE_SSE=1` it emitted a synthetic text Response and the CLI emitted `item/completed`, `thread/tokenUsage/updated`, and `turn/completed` (status `completed`). `ZCODE_CODEX_PROBE_NO_REASONING=1` set request effort to `none` but Codex still included `reasoning.encrypted_content`. These are isolated control/protocol observations, **not** real Provider or model-route certification. Before claiming host-managed support, record the actual Responses HTTP paths, fields and auxiliary calls made by this pinned version against a synthetic local Gateway. A local protocol probe may use a fake provider and isolated worktree without actual credentials, but does **not** establish model quality or Provider identity. The Gateway must preserve tool-call/result pairing, system/developer instruction hierarchy, structured errors, streaming deltas, cancellation and usage; unsupported features must reject the turn before any side effects, not silently drop them.

## Independent Model Gateway slice: Codex 0.157.1

On 2026-09-28, the installed `/home/ykzheng/.local/bin/codex` reported `codex-cli 0.157.1`. The installed standalone release directories contain 0.153.4, 0.154.0, and 0.157.1; there is no 0.156.1 binary available in this environment. The 0.157.1 experiment below is a new compatibility row, not a replacement or upgrade claim for the historical 0.156.1 probe.

The opt-in command `ZCODE_CODEX_GATEWAY_PROBE=1 node --import tsx packages/services/test/fixtures/probeCodexModelGateway.mjs` asserts the CLI version before starting. It uses Gateway 0.1.0, a temporary HOME, mode-0700 CODEX_HOME, temporary working directory, random Gateway token, and only a 127.0.0.1 listener. It never copies a personal profile or credential. Its only observed HTTP route was `POST /v1/responses`; it used a fake injected Model and made no Provider/API request.

The trace observed the same twelve top-level request fields as the 0.156.1 probe, with `stream:true`, `store:false`, `tool_choice:"auto"`, `parallel_tool_calls:true`, `reasoning:{effort:"none"}`, and `include:["reasoning.encrypted_content"]`. Input contained text message items with developer/user roles and text parts. `client_metadata` contained the known session/thread/turn identifiers plus Codex installation/window/turn metadata; all were strings, and `x-codex-turn-metadata` was 693 characters in the isolated observation. Codex also sent a 36-character `prompt_cache_key`. Gateway 0.1.0 pins the session/thread IDs to the grant, bounds metadata, and explicitly does not forward or claim support for prompt caching.

The probe disabled the optional `web_search` and `multi_agent` features using `web_search="disabled"` and `--disable multi_agent`, as documented by [Codex config basics](https://learn.chatgpt.com/docs/config-file/config-basic). The resulting tool array contained seven Responses function definitions; other tool variants are rejected. The text request completed. A streamed `exec_command` function call completed a tool roundtrip, and its follow-up `function_call_output` (including the item `id`) returned through the Gateway to the Fake Model. The fixed tool wrote only `gateway-roundtrip.txt` under the temporary cwd and exited successfully. The fake usage snapshots were input/output/total 12/3/15 for text, 12/8/20 for the tool call, and 12/3/15 for the follow-up; Codex emitted `thread/tokenUsage/updated`. A final hanging Fake Model request was cancelled with `turn/interrupt` carrying both `threadId` and `turnId`; the Model observed the propagated abort signal.

This container's `workspace-write` mode failed before executing the tool because Codex reported that its app-server socket directory did not satisfy the user-owned mode-0700 check. For this fake-only probe, `thread/start` therefore used `danger-full-access`; the only request and command are hard-coded in the probe, the command uses a relative file in the temporary cwd, and the probe asserts that cwd and exit code. This is not evidence that the CLI's workspace-write sandbox works here.
