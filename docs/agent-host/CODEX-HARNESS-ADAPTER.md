# Codex app-server HarnessAdapter (P5 PR09)

Status: explicit experimental factory, fixed to Codex CLI/app-server 0.157.1. This is a control and local Fake Model integration slice. It is not a live Provider certification, a production-default registration, or P5 completion.

## Boundary and ownership

The adapter implements the existing `HarnessAdapter` contract and is registered only by the explicit `createExperimentalRegistryCodexHarness` factory. It does not modify `SessionHost` or duplicate its command admission, idempotency, journal, or accepted-input state. The existing target composition remains responsible for creating the registry and choosing when to register this adapter.

- `SessionHost` owns `hostSessionId`, Host `turnId`, `runtimeEpoch`, command IDs, admission, canonical event sequence/journal, per-send binding audit facts, uncertain-send facts, and subscriber lifetime.
- One Codex adapter runtime owns one `codex app-server` stdio process, one isolated profile, the opaque backend `threadId`, backend `turnId` mappings, exact pending JSON-RPC IDs, and that session's Gateway grant. No process, profile, grant, native thread, or tool context is shared between Host sessions.
- Model Gateway owns grant authorization, one bound Model, route fingerprint, request/output budgets, request cancellation, and bounded turn leases. Each Host send supplies one frozen per-turn plan and Model; grant `sessionId` is `hostSessionId`, and grant `modelBindingFingerprint` is that plan's `catalogFingerprint`.
- Codex app-server owns native conversation history, model/tool loop, shell/file execution, and the decision point that waits for command/file approval.

```text
Host captures snapshot -> plans and binds Model -> Codex idle rebind/preflight
  -> CommandJournal durably accepts commandId + non-secret binding fact
  -> Codex begins matching Gateway turn lease -> turn/start on the bound native thread
  -> app-server streams item and turn notifications; adapter drains stdio continuously
  -> Responses call -> loopback Gateway grant -> bound Model -> Responses SSE
  -> app-server runs its own tools and may send an approval JSON-RPC request
  -> adapter publishes interaction.requested and retains exact rpcId + turn/epoch fence
  -> Host validates resolveInteraction -> adapter answers that rpcId -> app-server continues
  -> app-server terminal notification -> canonical turn/message/tool/usage events in Host journal
  -> Host ends the matching Gateway turn lease
```

The adapter translates events only; it never executes a Codex tool or accepts another input while the Host's turn is active. `commandId` is for Host admission and is not converted into a second adapter queue or retry key.

## Protocol and version boundary

The supported process is the exact `codex-cli 0.157.1` build. Discovery uses an explicit executable path or the necessary inherited `PATH`, then verifies the version with isolated `HOME`, `CODEX_HOME`, and temporary directories; the opt-in Gateway probe accepts `ZCODE_CODEX_EXECUTABLE` or `PATH` and uses the same version gate. The test-only schema fixtures under `packages/services/test/fixtures/codex-app-server-schema/0.157.1/` are generated with `codex app-server generate-json-schema --out <temporary-output-directory>` from that executable; their README records byte hashes and license provenance. The adapter starts `codex app-server` over stdio, sends `initialize` with the pinned build's experimental API capability enabled for Host-routed approvals, then `initialized`, and uses JSON-RPC requests/notifications from that schema. It never scrapes TUI output. A missing CLI, version mismatch, unexpected thread identity, malformed protocol line, or unsupported app-server request is an explicit capability/runtime failure. A version mismatch makes the session history-only; it never silently resumes a different CLI build.

New sessions call `thread/start`, store the returned `thread.id` unchanged in `BackendBinding.backendSessionId`, then send user input only after a Host `send`. Reattachment calls `thread/resume` with that stored opaque ID and does not issue `turn/start` or replay prompt text. An existing in-memory process can be reattached only when both backend thread and runtime epoch match. History remains in the Host journal and the Codex isolated profile; termination does not delete history.

Each Host session uses a mode-0700 profile/root under the adapter's target-local data root, with its own `HOME`, `CODEX_HOME`, and mode-0700 temporary runtime path. Its TOML config points only to the loopback Gateway and names a per-session environment key for the short-lived Gateway bearer grant. The adapter passes only a small process environment allowlist plus that grant token; it never reads, copies, or modifies the user's Codex config/auth profile, and it never gives Codex a real Provider URL or Provider key. The key is not placed in argv or logs. Spawned command environments use `inherit = "none"` and receive only explicit session-local `PATH`, `HOME`, `CODEX_HOME`, and temporary paths; the Gateway token is explicitly excluded, login shells and inherited shell snapshots are disabled.

The 0.157.1 profile disables Codex optional `web_search`, app integrations, remote plugins, and multi-agent features until their auxiliary routes are supported and tested. The observed request set is `POST /v1/responses`; any additional path remains a structured unsupported Gateway response. Grant limits, expiry, revocation, disconnect abort, and one-active-grant-per-session stay enabled.

## Model and capability semantics

Codex top-level Responses `instructions` is passed through the narrow `ModelRequest.systemInstructions` field. Leading Responses input `system` messages join that same system instruction layer. Input `developer` messages retain `ModelInputMessage.role = "developer"` and the existing CLI Model adapter emits them as actual OpenAI Responses developer input items. System messages after user/assistant/tool conversation are rejected because lifting them into `instructions` would reorder meaning. The host-managed Codex route admits only Provider Registry entries configured for `openai-responses`, a selected model with reasoning disabled, and the fixed Gateway contract. Anthropic, OpenAI Chat Completions, and other models without this two-layer mapping are reported unsupported; they are not silently converted or sent with collapsed system priority.

The factory `createExperimentalRegistryCodexHarness` is explicitly opt-in and is not registered by the production/default service composition. Without exact Fake Model fixture compatibility evidence, `hostManagedSupport` reports `experimental`; the existing `SessionHost` admission path rejects it. The pinned end-to-end fixture can inject evidence for only its `fake-provider/fake-model` selection so it can exercise the complete control path. That evidence does not certify any real Provider/model combination. Each grant records the Host session, frozen catalog fingerprint, and actual bound Provider/model identity; it cannot be retargeted through request fields. `harness-managed` is unsupported in this factory; native Codex account auth is never an implicit fallback.

Supported events are visible agent text deltas/final messages; command/file tool start/result; usage replacement snapshots; turn start/completion/interruption/failure; and server-originated command/file approval requests. Each event uses the current Host `runtimeEpoch`, a Host turn ID, and `lastJournalSequence + 1`. Usage events replace the last known snapshot rather than accumulating it. Unknown notification types are ignored as non-authoritative diagnostics; unknown **requests** are answered with a JSON-RPC unsupported error and surfaced as a session error.

For each supported approval request, the adapter publishes `interaction.requested` only after validating thread ID, active backend turn ID, item ID, and JSON-RPC request ID. Its public interaction ID includes the originating runtime epoch and Host turn; it privately retains the exact native request ID with `(hostSessionId, runtimeEpoch, hostTurnId, backendTurnId)`. Public message and tool row IDs also include the Host turn because Codex native item IDs can be reused. Resolution dedupe keys are turn-scoped; an old answer cannot release a new pending request even when the server repeats an RPC ID. An allow decision answers the exact retained request with Codex's `accept`; deny answers with `decline`, before app-server executes the requested command/file change. A stale, duplicate, missing, or foreign interaction is rejected. A late stop is sent only for the exact current Host/backend turn pair; a terminal event from an older backend turn cannot finish or cancel a newer Host turn.

## Process lifecycle and recovery

- Renderer/view detach only removes the view subscription; the target-local Host continues draining app-server output and writing its event journal. Adapter termination is never used for view detach.
- `terminate(hostSessionId)` stops and revokes only that session's app-server process and Gateway grant. Each Codex session has a private process, so no shared-process reference count is needed. Its on-disk thread/profile remains readable.
- Target shutdown stops only runtimes owned by that adapter instance. An active turn at process exit is reported `execution-unknown`; the adapter does not claim cancellation or replay input.
- Process crash, malformed stream, or broken pipe while a send may have executed marks the turn/session uncertain and revokes its grant. Cold `SessionHost.open` attaches with `thread/resume` and restores history without resending input; that path is exercised through Host. The `resumeExecution` capability remains unsupported because it would require replaying or continuing an uncertain in-flight turn, which the existing Host command journal blocks.
- `turn/interrupt` includes both the bound `threadId` and current backend `turnId`. It is not sent when either fence no longer matches.
- A Gateway grant is short-lived and can be renewed only without changing its immutable Model/route. The adapter opens a target-owned turn lease before `turn/start` and renews it while that exact Host turn is active, independent of any GUI connection; terminal/stop handling closes it. This keeps a long tool from losing Gateway authorization before Codex's next Model request. If an idle send needs a new catalog binding or the grant has expired, the adapter revokes the old token, starts an isolated app-server with the new token, and resumes the same opaque thread using `thread/resume`; it never replays prompt text. A catalog update cannot mutate an active turn. Explicit auth revocation and stop still fail closed. No automatic route fallback is allowed.

## Acceptance

Use `SessionHost` with the actual pinned CLI and this HarnessAdapter, a deterministic Fake Model, an ephemeral loopback Gateway, an isolated temporary workspace/profile, and no external Provider. Cover two isolated sessions, text, a multiple-call tool batch and paired outputs, command approval accept and deny (assert denied command had no side effect), cancellation, history/open/thread resume without prompt replay, target/process crash and unknown state, version mismatch, and observed auxiliary HTTP paths. Assert the grant matches Host session/catalog fingerprint and bound actual Model; assert no global Codex profile access, Provider/API network, SSH, or credential import. The real CLI test may exercise only fixed deterministic commands; it is not a claim that `workspace-write` sandbox works in this container or that arbitrary user tools are securely contained.

### Current resumed validation (2026-09-28)

On 2026-09-28 the opt-in pinned suite passed 5/5 against CLI 0.157.1, an ephemeral loopback Gateway, temporary profiles/workspaces and Fake Models. It covered two isolated threads, visible text, paired function calls/outputs, token exclusion from shell commands, cancellation, history resume without prompt replay, explicit rejection after selection revocation, a catalog update during an active turn without changing that turn's route, idle route rebind with token rotation and same-thread `thread/resume`, a short-TTL clock jump with same-binding grant renewal, and a controlled long tool that crossed the old TTL before the next Model request was authorized by the target-side turn lease while no GUI was attached. The existing fixed-command approval test covered real app-server approval requests and a concurrent allow/deny single winner. A separate Host+V4 bridge/transport test reused JSON-RPC ID `7` on successive Host turns, rejected the old UI interaction ID, and confirmed only one answer reached the new request. The registry-factory test confirmed exact Fake Model fixture evidence and that the factory remains experimental. These tests used no Provider/API, SSH or user credentials; the fixed-command fixture used `danger-full-access`, so it does not certify sandbox isolation.

`workspace-write` remains unverified here. The pinned helper tries to use `/tmp/codex-daemon-<uid>`, whose existing directory is owned by the current user but mode `000`; the environment mounts it read-only, so the required mode-0700 repair is unavailable. The profile still defaults to `workspace-write`, and its execution failure is surfaced rather than retried in full-access mode. An early exploratory start triggered Codex's default unauthenticated GitHub plugin-catalog refresh; the isolated profile now disables `apps`, `plugins`, and `remote_plugin`, and a later egress trace showed only the loopback Gateway connection. No model Provider/API credential or SSH route was used. Live Provider certification, working `workspace-write` sandboxing, arbitrary-tool safety, and the rest of the P5 acceptance matrix remain open; this validation does not mark P5 complete.
