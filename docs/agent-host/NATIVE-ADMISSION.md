# Native owner maintenance admission and configured metadata path

Native CLI worker owns the V4 CommandInbox and its live runtime. A trusted Node-local owner may request freeze → inspect fresh activity → automatic maintenance → release; browser/remote GUI cannot request freeze/release. Frozen means new create/send/resume and internal automatic admissions are refused at the CLI owner, not held for post-maintenance replay. Existing identical command retries, command query and read-only history remain usable; cancel/stop and interaction resolution of already accepted work remain usable. Freeze has a random process-epoch lease; stale release cannot clear a new lease. Crashes, lost owner connection, failed maintenance and uncertain activity block automatic maintenance, not implicitly unfreeze a still running worker. Explicit operator stop is a different path.

```text
trusted Node owner → current worker control request → inbox freeze (sync)
                                             → fresh activity snapshot
                                             → maintenance only if quiescent
                                             → release same lease + epoch
client → inbox → reject new admission while frozen; duplicates/query/cancel still resolve
```

Owner is the worker process; existing CommandInbox is the only serial input admission owner. Freeze is installed synchronously before any await in command handling or snapshot collection. No pre-freeze asynchronous lookup can commit a new admission after freeze: recheck at the final admission decision. Unknown runtime/tool/approval/queue facts block maintenance. Internal timer/auto-drain may finish already accepted work but cannot originate new user intent. Desktop continuous and mobile replayable subscriptions retain existing ordering and do not become control authority. Node port must target the existing worker (never spawn on inspection). Epoch/lease must not enter storageState/startup notification or ordinary persisted settings.

Native metadata path is a read-only *path resolver*, not a DB opener: use the same config precedence and resolution used by bootstrap startup, with native launch cwd explicitly supplied for relative settings. No migration, no file writes. `startup/storageState` remains databaseId-only. Missing config/worker identity is not a reason to guess a default for a different worker.

Acceptance: deterministic pre-freeze-await race; pinned duplicate, query, cancel, new create/send and release mismatch; real worker round-trip; custom relative path from env/config and cwd; no DB creation on path lookup. A count of GUI-visible running turns alone is insufficient for safe automatic maintenance.

Implemented boundary: `@zcode/adapters/config.resolveNativeSessionDbPath({cwd, env?, userConfigPath?, skipUserConfig?})` reuses `resolveConfiguredSessionDbPath` called by bootstrap `getSessionDbPath`. The lookup suppresses diagnostic disk logging and does not open/create the database. The caller must supply the *actual worker* launch cwd and config environment; for a missing/changed worker do not use guessed metadata. `@zcode/services/native-maintenance.getNativeMaintenanceControlPort(service)` is a Node-only factory lookup bound to the service's existing chat worker; no generic service RPC exposes it to renderer/browser. Existing-only lookup and post-response client identity checks reject worker replacement. `freeze/getActivity/release` are strict stdio control methods, with a random process epoch and lease ID; a failed control RPC is **unsafe**, never interpreted as zero activity. Native activity combines CommandInbox pending/in-flight/live accepted facts, projection queue/control/background/approvals, reverse interaction registry, legacy in-flight, resident active aborts, pending tools, and unknown cold/gap/faulted projections. The requester must reject on *any* positive count, unknown, lost worker or changed epoch, and recheck while frozen before automatic work. The port does not itself orchestrate Supervisor update/uninstall; the separate Host target gate and lifecycle integration remain mandatory.

Known conservative edge: unreadable/nonhydrated or detached live native projections mark `unknown`; lack of a complete independent timer/automation schedule certificate means a production maintainer must independently fence the upstream timer owner as well as this CLI ingress before declaring an automatic maintenance window safe. No `storageState` field contains the DB path, lease or credentials. The disposable child test drives the real protocol server + CommandInbox over stdin/stdout with no session store or daemon; actual packaged worker and Supervisor automatic maintenance remain pending gates.

## Protocol dispatch mutation coverage (native-mutation-fence)

The CLI protocol server owns the maintenance ingress fence, not a second command queue. Its explicit read-only allowlist covers conversation subscriptions/resync/unsubscribe/flow, page/history/attachment reads, usage and legacy session/workspace/plugin/workflow list/get/overview/debug/capabilities. Explicit accepted-work controls cover legacy stop, background/model/plugin cancellation and attachment abort. Every other dispatch (including unrecognized methods) is a potential storage mutation or new execution: trust grants, provider and interaction/model-I/O/off-peak/dynamic-workflow policy changes, plugin marketplace/config/install operations, workflow write/move/delete, attachment upload transactions, connectivity/model execution and legacy session mutations. The V4 `command` method is also counted at protocol ingress across the residency await (conservative pending, not another queue), then uses the **same** CommandInbox; its final admission check permits exact accepted retries and stop/resolveInteraction/cancelBackgroundWork/deleteQueueItem but rejects new execution while frozen. Reads, query and accepted-work controls do not become a path for new user intent.

```text
request → synchronous classification + in-flight mutation counter → residency await → fence recheck → dispatch
                                           ↑                                ↑
trusted freeze → same CLI CommandInbox lease + protocol lease (no await) → snapshot pending counter
            → drain or reject automatic maintenance → fresh getActivity under same lease → release
```

The counter is acquired before first await and released in `finally`, including failures and rejected writes. An operation admitted into dispatch before freeze may finish its durable write; the frozen activity snapshot remains non-idle until it does. A request waiting on residency when freeze arrives must not dispatch. Unknown future dispatch methods fail closed under freeze, and cannot silently bypass the counter. The process-epoch lease and stale/terminated-worker behavior remain unchanged; release never asserts durable completion, and crashes/uncertain I/O are not equivalent to idle. No extra persisted queue, public Node RPC, or Desktop/mobile delivery behavior changes. Acceptance includes concurrent trust/policy/preferences writes crossing freeze, actual durable write timing, stale release and termination over disposable subprocess stdio; no user profile or provider call.

Termination race: a request that was awaiting residency when shutdown set the runtime stopping bit cannot dispatch a write after the await. The server checks runtime liveness again immediately before dispatch. Already-dispatched writes are *not* implicitly cancelled by this guard; maintenance must drain them before stopping the worker, or treat lost/uncertain completion as unsafe.
