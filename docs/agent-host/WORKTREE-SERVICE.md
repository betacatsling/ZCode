# Target-authoritative worktree registry

The target-local WorktreeService is the sole writer of versioned binding/workspace records, generations, removal state and admission gate. Profile Catalog owns project names, titles, order and visibility; the target registry does not infer identity from tabs, branch, origin URL, remote connection ID or pathname. An executionTargetId namespaces the storage and every binding; target-local repository instance evidence combines the device/inode of Git's common directory with a target-namespaced random marker written in that directory on registration. Workspace instance evidence combines the Git administrative directory's device/inode with its own target-namespaced random marker. Inodes alone can be reused after delete/recreate. Read-only discovery does not create markers; explicit registration does. If evidence cannot be obtained, do not claim an existing identity. An explicit adopt/create supplies a new workspace ID. Never automatically adopt a recreated path.

`inspectRepository` and `reconcile` are read-only Git scans. An unsuccessful scan does not replace the previous tree. A missing/rebuilt path becomes needsVerification and history remains readable, but admission is denied. A Git branch rename or worktree move retains the ID only after matching Git administrative directory identity/marker and repository common-directory identity/marker; otherwise it is a new unregistered candidate requiring explicit adoption. If the repository anchor itself moves, `reconcile(bindingId, newRepositoryPath)` explicitly reanchors only after the same-instance checks pass. A bare repository has no runnable main workspace; an existing main checkout can be explicitly adopted but never deleted by linked-worktree remove. Cwd is canonicalized and checked against the verified worktree and Git's nearest repository, preserving relative legacy subdirectories; symlink escapes and nested repositories/submodules are rejected for that workspace.

State transitions (`create/adopt`, `verify`, `remove`, `reconcile`) run through one target owner with a durable atomic versioned snapshot and exclusive owner lock. Another owner must fail closed; an unclean owner's lock requires explicit `recoverStaleOwner` recovery only after the former PID is definitely absent (PID reuse or inaccessible processes fail closed). A successful Git create followed by persistence failure leaves a discoverable **unregistered** candidate; do not delete its directory or branch. A write failure after assigning an instance marker likewise leaves a discoverable candidate for explicit re-registration. If Catalog persistence fails after target registration, `reconcile` still returns the target record; Catalog must compare target records with its durable IDs and surface an unmatched target record for explicit recovery, not silently route or discard it. A pending removal is durably persisted before Git mutation; restart reconciles the outcome before any admission. A removed record is retained for history and never routed to a new path instance.

Event order for new session/send: target route → acquire workspace gate → verify stored generation and Git admin/common identity → canonical cwd/Git membership → execute Host create/send callback while lock held → release. Event order for removal: freeze gate → confirm explicit user authorization → consult authoritative native/external runtime activity (waiting/running/tool/unknown/offline unsafe) → verify Git/identity and Git preflight → persist pending removal → recheck activity and Git preflight → non-force `git worktree remove` → persist removed. No session is terminated implicitly. Busy sessions reject removal, not vice versa. Filesystem facts alone cannot prove that all external writers are absent: UI must disclose the risk and require confirmation. If Git succeeds but final persistence fails, pending removal remains and restart reconciliation marks the tree removed. Branch and history are preserved. No pruning or forced deletes.

Target owner lock is process-exclusive with an opaque token and snapshot revision fencing. Files are async-written to temporary files in the same directory and atomically renamed. No profile or remote cache can assert target filesystem facts. This service does not compose global desktop/remote wiring; that integration belongs to its owner.
