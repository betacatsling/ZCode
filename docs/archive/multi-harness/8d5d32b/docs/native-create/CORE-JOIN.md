# Core → native create join (new agents; default OFF)

## Pre-init activation boundary (boot-only follow-up)

### Connected public process acceptance (manual continuation)

The actual Core factory's held lease and the selected CLI CommandInbox are separate gates: a CLI byte arriving before construction is not an accepted command until its stdio dispatcher handles it; if dispatched under the boot fence it must return held, not execute. The Core must expose read-only reconciliation while held, deny external Host execution before the same held lease is released, and only the exact selected worker release ACK may open Target/Host and native admission. A test fixture may coordinate before Core's READY publication; READY publication is not itself the internal release and delaying it is not a surrogate for preconstructor execution. A cold CLI store with prior accepted ordinary input must be observed via real public requests, not fabricated SQLite rows; pending/unknown create receipts must not be promoted by reopening. If current source offers no autonomous replay, record that limitation rather than pretending it resumed. Wrong, stale and disposed releases stay closed; shutdown of each fixture process and upstream is bounded. Native create production remains disabled.

```text
Core held lease → CLI spawn/early stdio bytes → CLI constructor installs CommandInbox hold
  → storage + CLI claim → readonly Core reconciliation → Host attempt denied
  → exact worker release ACK → Target admission open → Host/CLI new request → fake Model HTTP
  → terminal event; cold restart only on explicit guarded request (no implicit replay)
```

Held Core owns the workspace/Target admission lifetime before preparing storage. The selected CLI's single CommandInbox owns native accepted commands and freezes synchronously in the protocol server constructor; storage preparation and readonly reconciliation are permitted while held. Registry config startup currently precedes the constructor and can schedule config refresh checks; MCP pool construction also precedes it but creates only an unconnected lease. Neither path itself calls Model/tools. This observed ordering alone is not evidence of an unauthorized business execution; the CLI must not start stdio or cold session hydration until after its Inbox fence. Transport input is not serviced until after construction and startup; no cold session or queued input is automatically replayed by opening SQLite. Cold session hydration requires a later protocol request. A persisted ambiguous create receipt remains pending and cannot be promoted by startup or retried on release. The connected acceptance uses the real `runServerCore` caller with a wrapper that creates the public authority in `held` mode, completes the real reconciliation, and pauses immediately before Core binds HTTP/publishes READY. During that barrier, call the real Host API with a previously persisted Git/Catalog workspace and send a valid native V4 command to the selected CLI; both must refuse without changing SQLite or contacting Model HTTP. A separate CLI wrapper buffers a valid V4 `sendText` frame into the actual spawned CLI stdin before releasing a preload barrier, proving the frame precedes CLI module construction rather than merely preceding READY. The seed history is created only by public CLI `createSession` and `sendText` commands in an earlier open authority; cold reopen may expose that history but must not execute it again. After Core publishes READY, only the original boot lease's awaited CLI release ACK permits a fresh Host/Pi Model turn; READY publication and internal catalog reconciliation are not admission ownership.

```text
Core held workspace + worker-spawn gate
 → selected worker storage preparation (no business RPC)
 → normal CLI opens SQLite → Registry config/refresh + unconnected MCP lease
 → constructs server / installs CommandInbox hold → broker setup → starts stdio transport
 → Core claims SAME worker/epoch, reconciles readonly → Supervisor commits
 → exact release ACK opens CLI Inbox and workspace → fresh Host/native requests
```

The current server receives initialized Registry/MCP dependencies before transport starts; requests cannot observe an unset runtime. A failed/cancelled startup closes server/storage/Registry/pool without accepting business requests. Whether a future Registry/MCP implementation adds a business-capable preconstructor callback remains an explicit compatibility boundary, not an inferred current bug. External Host create/attach/new commands cannot materialize a trusted adapter before boot release; completed-create queries and history remain readonly. Boot claim itself must tolerate accepted/pending history; ordinary maintenance requires a fresh idle census and rejects running/waiting/unknown. On stale/disposed/rotated worker or lost release ACK, keep admission closed. New workspaces after release must use the dynamic open state, never an immutable initial-held flag. The production Native create gate remains OFF and this does not authorize arbitrary old CLI artifacts, attached remote routing, or completed-only metadata repair.

Acceptance: actual selected CLI startup under held Core, storage state and readonly history before release, no Model/tool/MCP execution while held, real external Host create/attach denied before adapter activation, positive fresh input on same owner after release, cold persisted ordinary inputs only activated by guarded explicit request, pending/unknown creates not retried, wrong/stale/disposed release blocked; repeat with second worker and maintain fresh-idle semantics. External/Desktop route authentication is separate.

Core Catalog and Target own the project/binding/workspace/generation; CLI CommandInbox and SQLite own original native IDs, actual runtime configuration, receipt and accepted commands. Core owns only a **new** verified mapping (not `native-migration/mapping.json`, which is backup-verified legacy evidence). Desktop continuous and mobile replayable are distinct deliveries of one CLI owner.

```
Catalog immutable intent + Target verified scope/generation
  → hold Target admission → CLI capability + configured DB identity check
  → CommandInbox createSession(commandId, workspaceId=identity||path, config, NO firstInput)
  → CLI persists actual selection/execution facts and completes receipt
  → Core read-only verified completed receipt + persisted facts
  → Core fsync new mapping + Catalog reference → return original native ID
retry/lost ACK → read-only receipt + exact intent/scope/generation check → same mapping/ID
```

No receipt, pending receipt, unsupported schema, unknown/old CLI capability, incorrect actual selection, unknown DB path or failed fsync is **uncertain**, not success. Never replay a pending create or synthesize input to complete it. Query of an already completed command is read-only even when new admission is disabled; new creation remains disabled by default until all join proofs pass. Never infer runtime configuration from the receipt's intent fingerprint or from current workspace defaults. `workspaceIdentity?.trim() || workspacePath` is the identity key; path is for filesystem operations only; remoteSessionId is attachment authority, not a path alias. Real configured DB is resolved against each native worker's actual cwd/env, including relative override. Core lock does not purport to lock independent external CLI processes or every configured DB globally. Crash lock recovery requires ownership proof stronger than PID alone and is not automatically enabled.

Acceptance: real isolated Git/Target/Catalog/Core factory/native CLI/SQLite, two agents in one worktree without more Git worktrees, actual Model fake HTTP only; normal and matching-default config survive CLI+Core restart and changed defaults, actual next Model request; lost ACK after completed receipt, failed mapping commit, pending receipt, wrong scope/model/generation/lease, old capability and malformed schema fail closed with unchanged session/HTTP counts. Read-only reconciliation works while new admission disabled. Native first input/queue/legacy empty draft and side-session behavior must not change. Freeze includes three worker lanes, automatic ingress and timers; cancellation/query still lawful. Supervisor replacement-generation fence remains separately owned and does not become certified here.

## Separate new-create journal (incremental implementation; not certification)

The Core journal, when mounted by the factory, lives under `native-create/` in the Core profile, separate from the backup-verified `native-migration/mapping.json`. Before any CLI command, it writes a strict immutable intent keyed by command ID: Catalog project/workspace/binding/generation, Target, identity key and path, remote attachment if any, requested model binding and relative cwd, and the configured source DB identity. A different payload for an existing command ID conflicts before effects. An intent with no completed certified CLI fact is uncertain (including a pending receipt), not permission to allocate another ID. Only after a read-only, scope/config-verified completed fact may a distinct mapping file commit the original ID. An already committed mapping is immutable and may be queried without starting the worker or opening new admission. Every rename and parent directory is synced; failed commit is an error, not ACK success. Read-side schema/identity/provenance mismatch fails closed. Journal files are not CLI session or task rows and are not legacy backup claims. The journal alone does not validate Target generation or authorize a live command: Target must hold admission while writing intent, checking capability and dispatching to CLI. A caller must compare the actual certified config to the requested selection, not only the immutable fingerprint.

Mount decision: `createCoreAuthority` alone opts into a test-only native gate (default OFF); the public hierarchy keeps Target admission and Catalog owns project/binding/generation. The Node service's current chat worker owns client and worker generation; CLI reports its actual opened DB path rather than Core reconstructing spawn cwd/env. CLI owns storage startup, capability and original-ID allocation. No renderer-visible client handle. Before dispatch, Core stages one immutable command intent under the profile owner. After a completed CLI fact, the journal certifies the original ID; if dispatch ACK is lost, a read-only receipt query may complete the mapping, never resend. A pending or conflicted receipt stays uncertain. Read-only directory joins the distinct new mapping source with legacy backed-up mappings; a new draft must not appear as a duplicate legacy task. Exact DB identity, workspace identity and Target generation must match, including retry after restart. No activity/freeze or sender-side overlay is an authority substitute.

Current status: public Node `createCoreAuthority` mounts this journal and directory behind `ZCODE_CORE_NATIVE_CREATE_TEST_ONLY=1` (default OFF). The Node-only WeakMap port obtains live CLI `runtime/capabilities.nativeCoreCreateV1` and readonly `runtime/nativeOwnerDescription` from the opened SQLite store, matching the same client's ready databaseId and managed worker generation. Core stages Catalog/Target-derived intent, dispatches exactly one V4 Inbox create without firstInput, certifies the completed receipt and immutable actual selection, then commits a separate mapping. Directory reads join that mapping without claiming a legacy backup; completed retry works with new admissions or the test-only flag OFF. The public-factory tests verify two original IDs in one Git worktree, absolute and relative DB overrides, service→Core completed ACK loss, post-rename/pre-fsync failure not reporting success and rolling back the visible mapping, changed-default restart, and real terminal fake-HTTP input with the original requested model. A pending receipt remains uncertain. Durable Catalog reference beyond the directory's mapping-backed join, remote same-path owner proof, old-capability/stale-worker/unknown-schema/binding-generation/pending factory negatives and full freeze/lifecycle/crash-owner proof remain **unclosed**. This is not full Core certification or production enablement.

## Factory boundaries pass 1: scoped read degradation and attachment gate

The authenticated remote authority is the **window connection registry** (`windowRemoteConnectionRegistry`) and its scoped service attachment; Core's target-local worker is not itself an authenticated SSH attachment. No public factory create is permitted to claim remote attachment authorization using a caller-supplied ID, Catalog path, or a constant resolver. Until Shell/Supervisor routes an authenticated scoped request to the target Core and rechecks the window generation around acceptance, remote creation must stay unavailable. A stored `remoteSessionId` is creation provenance, not a current write lease. Local path fallback remains unchanged. The exact protected interface request is in `.tmp/interface-handoff.md`.

```text
window authenticated registry (identity + path + logical session + generation)
  → scoped target Core service → Target admission → CLI owner / CommandInbox
                                            → completed CLI receipt → journal mapping → Catalog reference
reconnect → new authenticated registry attachment → readonly original receipt (no effect/replay)
```

The Node-local creation port must compare the process manager's typed runtime identity **and generation** and the same client's ready DB state before effect and after ACK. If ownership changes after an effect may have committed, report uncertain rather than converting its SQLite receipt into a writable factory result in the same request. A later read-only retry is a distinct Target/Catalog-authorized reconciliation; no replay. Target admission remains held through Catalog commit.

For local source history, a broken _single new mapping_ (malformed file, missing receipt, corrupted or unsupported source DB) cannot grant a writable owner and must not mask unrelated certified mappings. Journal read returns only individually re-certified mappings and provides per-entry diagnostics keyed by hashed filename (no secrets/paths), with no mutation or CLI spawn. Top-level directory/legacy backup failure remains an error, never a fabricated empty sidebar. Direct `read(commandId)` remains strict, so a damaged command cannot become an unrelated new allocation. Each entry is checked against its own configured nativeDatabasePath; bootstrap DB attestation alone is insufficient. The legacy migration backup still requires its bootstrap DB attestation; with _only_ individually certified new mappings the unrelated boot DB must not veto them. With no certified mappings/legacy source, retain the bootstrap DB check (not a fake-empty result). Test with two real CLI-created receipts in distinct valid source scopes and corrupt one source, assert other survives, broken ID is not writable, no new effect. Source DB schema mismatch is quarantined with a diagnostic, not automatically repaired.

## Catalog reference commit (mount-2)

Catalog owns a separate durable reference per native command: original ID, project, workspace, binding, generation, identity and path. Core journal remains sole immutable intent/mapping owner; CLI remains sole session/config/receipt owner. After CLI completed fact and synced journal mapping, the Target admission lease remains held until Catalog's serialized profile commit of an exact reference. Return success only after that commit; failed Catalog commit is uncertain, never a second CLI allocation. On completed retry (even with new admission disabled), re-certify the mapping from the CLI DB, then idempotently repair the reference only when current Catalog binding/generation/identity matches. Directory exposes new mapping only when a matching Catalog reference exists; missing reference stays invisible until repair. Catalog mutation cannot forge a CLI receipt or modify session business rows. Legacy backup mappings remain independent. A stale binding/generation must never repair a reference. Source DB and scope are verified per mapping. This is not a global CLI database lock or a claim of full lifecycle closure.
