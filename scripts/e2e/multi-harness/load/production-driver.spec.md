# Load runner and production-driver contract

## Runner module boundary (Sol extraction)

The runner remains the only owner of fixture, sample schedule, result and cleanup state. To satisfy the 400-line source policy without suppressing it, split pure fixture/options, provenance/comparison, cleanup/isolation, and result-shape construction into private sibling modules. `runner.mjs` retains the public exports and the sole `runLoad` event loop; imported helpers cannot accept commands, mount a view or create a second owner. Existing runner tests and CLI subprocess results must remain identical. This is a structural change, not mounted-product evidence; the actual Core→utility Host→Shell paint requirement below remains open until an executed browser assertion observes that route.

## Ownership and event order

The runner owns the disposable Git fixture, schedule, result artifact, provenance snapshots, baseline comparison, and cleanup registry. The CLI owns only argument parsing and process-exit reporting; its exit code is derived from the same persisted run status. `createProductionBackend.emitCommitted()` is a lower-level durability diagnostic only. The opt-in short load path instead sends a real `AgentHostTargetService.dispatch(send)` command per turn: Host admission and its command journal accept the command before the trusted fixture harness starts, and the harness pauses after durable `turn.started` on an owned gate. Host remains the sole owner of accepted commands, event sequencing, and durable journal writes. The driver keeps only a bounded, O(1) handle for each currently active accepted command and drops it at terminal/cleanup; retry/dedup authority remains the Host command journal. The fixture does not resolve a Provider, launch SSH/CLI, or write workspace files. Target owns Git discovery/lifecycle, Catalog owns adopted workspace references, and Host owns session/event state. Browser owns paint and drafts; the runner/driver cannot substitute synthetic values for browser evidence. The Shell/browser mount, paint sampler and separate process facts remain fail-closed until connected to this owner.

Sequence: create isolated external fixture and HOME/XDG/Desktop/Web profiles -> Target read-only discovery -> Catalog adopts real candidates -> Host creates ten sessions -> dispatch ten accepted `send` commands -> observe ten Host-owned running turns -> detach the view only -> prove same-command retry is a duplicate -> release the trusted producer gates -> commit bounded nonempty assistant text/tool lifecycles and terminal events -> query/replay by the last owner cursor -> close Host/Target/Catalog and reap every owned resource. Desktop continuous subscription and Web replayable query/snapshot/gap repair remain distinct. A fully connected browser run must additionally mount the actual Shell/Sidebar/Pane, inspect DOM and UI-consumed cursor, record painted input/switch samples, and collect separate Core/renderer facts; this checkout still fails that mount gate. No timeout substitutes for sequence completion. `committedEvents` counts Host sequence increments returned by the connected driver; a contract stub without owner cursors only counts its one scheduled call and is not product evidence.

## Provenance and outcomes

Each artifact has a schema version, actual Node/V8/platform/architecture identity, and hashes for the actual driver entrypoint and selected build artifact. The connected fixture's trusted harness does not emit events before Host accepts a `send`: it holds after `turn.started`, then releases a bounded seven-event turn (start, two nonempty deltas, tool start/finish, message finish, terminal finish). The first ten accepted commands are held simultaneously across the five adopted workspaces; activity/read-model and journal queries—not driver counters—prove that state. The legacy `emitCommitted()` helper is never used as accepted-command or renderer evidence. The runner snapshots the selected Git checkout (HEAD plus clean tracked/untracked status), loaded driver/support source files, build artifact, build-preparation manifest, and runtime identity before measurement and verifies those exact inputs again before writing the result. The production driver commit is independently checked against the selected checkout, not accepted from a self-report alone. For a non-contract-stub production driver, the actual loaded `.mjs` entrypoint must live within that selected checkout and be hashed before import and after measurement; CLI runner/facts/measurement source inputs are also snapshotted before driver import and rechecked after measurement; the checkout must have neither tracked edits nor untracked files. An external contract stub is only test evidence, never a mounted product driver. A comparator rejects missing/unknown schema or runtime/driver/source/build mismatches, same-commit baselines, changed/tampered source or artifact hashes, invalid sample population, and invalid preparation provenance. A build-success manifest proves only its declared source/artifact preparation; it does not prove the binary was mounted or rendered.

A CLI-loaded `contract-stub` benchmark is always `contract-stub-only` (exit 2), even if its arithmetic comparison is within budget; stub p95 values are never product paint evidence. `smoke-only` means a completed smoke, not a production pass. `latency-measured` is reserved for a comparable controlled benchmark within both <=1.10 p95 budgets. Failed work is `failed` (CLI exit 1); pending, unsupported, missing, or incomparable comparisons are explicit non-pass outcomes (CLI exit 2); only a completed smoke or valid within-budget controlled comparison may exit 0. Acceptance cannot silently pass while its comparison is pending. When `--baseline` is supplied, unreadable/forged/non-comparable baseline inputs must be reflected in the persisted status and nonzero CLI exit.

## Acceptance boundary

Acceptance remains 50 real worktrees (including main), ten sessions over five expanded workspaces, 100,000 committed Host events, eight hours monotonic, and separate desktop-continuous/web-remote-replayable runs. Require >=20 input and switch samples per session, separate actual host/renderer memory and owned child counts before/after cleanup, no implicit CLI launch, and read-only discovery. A smoke does not certify production. A comparable baseline must be preserved on the same hardware/config at a different commit; retain raw results and compare typed and switch p95 independently. Driver must fail closed until whole-Shell external owner attachment, actual browser paint/renderer consumption, and separate process metrics are available. No synthetic latency, renderer/cursor/CPU metrics, fake UI fixture, or successful build is evidence of a mount. Top-level `dispose()` is idempotent and works on partial open; `open` registers cleanup before async owner startup. Runner passes delivery explicitly, never inferred from argv, and driver rejects a mismatched source checkout. This backend's synthetic lifecycle is meaningful Host workload only; it does not establish product/UI acceptance.

## Connected short-product diagnostic (not certification)

The opt-in load fixture must use the public `AgentHostTargetService.dispatch(send)` on each of ten real Host sessions, not `harness.emit` outside accepted turns. A credential-free trusted harness owns one turn per accepted command and pauses on a fixture-owned gate after `turn.started`, keeping ten actual running turns across five Catalog-adopted workspaces while the 50 discovered Git worktrees remain intact. The Host alone owns command IDs, admission, durable sequence and replay. A repeated command ID cannot re-send on renderer detach. On release, each accepted turn emits bounded nonempty assistant text, tool start/finish and terminal events; `getSessionReadModel` and `eventsSince` are the commit evidence. `cancelTurn`/`terminateSession` release the gate and close every accepted turn finitely; no timer is a success signal.

```text
fixture send once → Host admission/receipt → harness gate/turn.started → Host journal
                                   ├ desktop-continuous subscription → Shell pane paint
                                   └ web-remote-replayable query(cursor) → Shell pane paint
view detach → owner continues → query previous cursor → reattach WITHOUT send
```

The UI diagnostic must actually mount `WorkspaceShellLayout` with the production client and owner-derived Catalog/hierarchy, type a draft and switch a real session in the painted renderer. A Node-only owner fixture remains partial evidence. Browser input-to-paint measurements require browser timestamps/RAF and matching visible session/draft/row IDs, never driver arithmetic. Read current Host snapshot and UI-consumed sequence separately; fail closed if their difference is unknown. A short diagnostic records separate Core/renderer PIDs, RSS/heap and cleanup, and does not claim benchmark comparability with built-unmounted 1e7, 8h or 100k acceptance.

Acceptance cases: 50 registered worktrees / five expanded workspaces / ten accepted running turns; 20 input+switch paint samples per session in a qualifying measurement; two delivery runs serially; detach/reconnect cursor continuity and unchanged command receipts; cancelled producer closes without orphaned child. Missing Shell, real paint, metrics or coverage is a failed/pending gate, not a synthetic PASS.
