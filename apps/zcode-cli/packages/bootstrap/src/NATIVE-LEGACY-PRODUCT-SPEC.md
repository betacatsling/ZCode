# Legacy Native product continuation (bounded)

An existing SQLite session is the original CLI owner. Public V4 commands must not replace its ID, transcript, permission or persisted selection. Snapshot is a view; Core's directory is a **separate** verified mapping/index projection, not an automatic inference from a SQLite row. Core history must never synthesize a migration mapping or accepted turn. Legacy migration requires the public `LegacyWorkspaceMigration` writer: export the actual native task index, obtain a verified target/worktree binding, back up that index, then apply the mapping. A factory reader alone must not write the sidecar. Missing index or mapping yields no certified owner; report the integration gap rather than claim a Core join from direct CLI traffic.

## Connected acceptance path

Seed an isolated pre-existing SQLite session with an original ID, custom title, explicit selection/execution state and permission. Drive a genuine public V4 turn through the real CLI and loopback Model so its native task-index evidence exists. Create the matching Git workspace through public Core Catalog/Target services. Then use the public migration writer with the actual configured database/index and Target-verified generation/binding. Before mapping, public Core `resolveOwner` must not invent an owner. After applying the verified mapping and cold-opening `createCoreAuthority`, hierarchy must resolve that same original ID as writable with its original scope. Route a subsequent real accepted V4 input to that returned ID and observe the same ID's terminal frame, SQLite history and exactly one fake Model call. This migrates metadata only: no replacement ID, transcript copy, fabricated receipt, replay, or directory-side write.

## Behavior regression

Issue public `createSelectionSideSession` against the original legacy ID with `firstInput`. Child must have a distinct stable ID, persisted parentID/lineage and its own persisted model selection, without rewriting the parent's messages/config. The child is a fork: committed parent history is copied into the child's own transcript; the side input is child-only. During a running turn, only the committed real-user input (not assistant/tool increments) may be copied. A duplicate command must not create another child or Model call; cold reopen must retain both IDs and lineage. The accepted input belongs to the child, and a real fake Model request proves execution; no synthetic acknowledgement stands for a turn. Failure refuses ambiguity; do not replay uncertain command effects. Fork/edit/retry require real stable targets; unsupported targets fail before mutation. For an actual assistant fork, capture the completed assistantText row's `{rowId, entityId}` and the current projection revision/logEpoch from the public V4 snapshot, then submit `forkAssistant` against that stable pair. The child receives a new ID, copies only committed parent context through the selected boundary and preserves the original parent's branch and selection; a byte-identical command retry yields duplicate without allocating another child. After a cold reopen the child parentID and copied content still exist. `editUserQuery` targets the latest real userInput row with its own current pair and replaces that turn in the same session (preserve workspace), while `retryTurn` targets the resulting latest completed assistantText row and replays the canonical revised user intent without creating a session. Each must generate a real provider request and terminal frame; old/stale row pairs must refuse mutation. Record actual row identities and provider request text; never guess rowIds from SQLite or synthesize snapshots. Source of truth is CLI CommandInbox admission and its V4 projection; Core routes to the same owner, not a second queue.

Event order: public snapshot (revision + epoch + stable row target) → CAS command to CLI → CLI admission/revision check → runtime fork or rewind/turn → SQLite commit + Model request → terminal frame → cold reopen. A retry of the exact commandId is idempotent even after the resulting revision changes; a fresh edit/retry needs a fresh row target. Desktop continuous frames and replayable cursor recovery are separately proven, not inferred from one another.

## Ownership and event order

```text
V4 command -> CLI CommandInbox admission -> runtime fork -> SQLite child + command fact
                                               -> V4 result / separate child projection
Core read -> verified task-index export + native metadata -> public migration backup/apply
           -> hierarchy owner -> routed V4 command to the same original CLI ID
```

Desktop `desktop-continuous` and mobile `web-remote-replayable` are distinct subscriptions to the same CLI session owner; neither detachment nor replay creates an accepted input. For a held running fake Model, admission and dedup are CLI-owned: issue first accepted command, observe the Model HTTP request still held, issue a second distinct accepted queue command, detach the continuous subscription and reconnect to the same CLI owner before releasing the first response. A duplicate second envelope cannot add a turn. Only two separate genuine terminal frames and two ordered Model requests prove drain; a transport snapshot is not proof that queued input completed. The web-replayable subscription must observe the same session owner without reissuing an input. No new client queue or query-side migration. Source DB/cwd must be the configured ones, and unknown provenance stays read-only. The limited fixture may use only loopback fake Model, isolated SQLite/profile, bounded cleanup. Acceptance evidence requires actual frames, verified migration backup/source rows, Core owner scope, persisted SQLite lineage and Model request counts; gaps remain explicit.
