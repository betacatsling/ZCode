# Core model message role compatibility

Core history owns runtime message entries; the contracts `ModelInputMessage` is the provider-facing input. Context construction supplies messages; Core must retain the source role, content and order through history clones, context entry conversion, request projection, reset and compaction. A `developer` instruction is distinct from system/user/assistant/tool: never stringify, relabel, wrap as reminder, merge with user text or infer an alternate role. No extra state, persistence path or provider override is introduced. Only the model adapter can decide if a selected API can represent developer; unsupported adapters reject before dispatch under their existing contract. Native requests without developer retain the identical projection, cache and provider behavior.

Boundary: `ContextBuildResult.systemMessages` may carry the public contract's role union. Core's local history message type must accept the same roles; history/compaction instruction prefix checks include developer. Projected user reminders do not cross a developer instruction in either direction: an attachment before a developer stays before it, one after stays after it, including multiple instruction boundaries and both mid-conversation-system settings; mid-conversation synthetic system reminders may only anchor at existing valid user/tool positions and must not rewrite a developer entry. Cache markers are not newly placed on developer as a non-system conversation item. No silent fallback to text/user/system. `ModelRequest` still uses the public contract type; Core only creates a request-local cloned projection. Event order: context build → Core history init/clone → per-request projection → adapter admission/dispatch. History remains sole owner; read-only projection neither mutates history nor adds retry state.

Interleaved developer instructions are not a compactible prefix: `system → user → assistant → developer → user → assistant → developer → user → assistant` cannot become `system → summary`, nor may a summary model silently absorb developer instructions as user text. Until a role-aware ordered compaction format exists, active compaction fails closed before any timeline event, model call, or history replacement when a developer entry occurs after the contiguous context prefix. The post-compact builder also rejects that input, including direct callers; history remains unchanged. A developer in the initial prefix remains intact. Without an interleaved developer, native compaction and request projection retain the existing behavior. Automatic/reactive compaction failure is explicit, not a successful fake boundary.

Acceptance: dependency-built `@zcode/core` typecheck and build both pass (not just root tsc); initial developer prefix survives init/reset, replacement and cloning with order and content; context conversion carries developer unchanged; projected mixed instruction/user/assistant history preserves role and serialization, including metadata/cache properties, while existing native role-only fixtures remain byte-for-byte unchanged; unsupported provider behavior stays under adapter contract and is not simulated by Core. Tests require no provider calls.
