# Supervisor generation and update transaction

Owner: Supervisor owns exactly one current child/generation, lifecycle gate, release pointer transaction and maintenance handle. Core's maintenance port alone owns admission/activity; CLI is not a second queue. Services CoreNative owns worker/timer ingress. No GUI detach or SSH loss causes lifecycle work.

```
control -> lifecycle gate -> capture child + generation -> Core freeze -> fresh census
  -> revalidate child + generation + lease after each await -> stop captured child/observe terminal
  -> write update transaction/current -> launch candidate fenced -> generation-ready
  -> complete pointer transaction -> release candidate lease -> admit
failure -> terminate candidate (confirmed OS terminal) -> restore pointer/transaction
  -> launch previous fenced -> generation-ready -> release previous lease
```

Unknown, missing IPC, failed release, waiting and running are unsafe for nonforce. Explicit force may interrupt activity but must still verify lease identity and generation. A stale reply, old release or old restart timer cannot authorize an effect on a new child. A maintenance request racing Core exit never transfers its lease; acquiring it after exit fails closed. A failed stop retains child/lock and `stop-failed`; no new Core may launch without confirmed terminal. If the update pointer transaction has committed but release acknowledgment is lost, do not roll back (the candidate may already have admitted work); preserve committed pointer, lock, child and `stop-failed` diagnostic for explicit intervention. The same rule applies to a rollback Core: if its boot-release request was sent and its acknowledgment is lost, preserve the previous pointer, live rollback child, lock and `stop-failed`; never stop the possibly admitting rollback child. Only errors before release dispatch (including readiness failure) may stop that held child. A subsequent exact-token release may query/retry; wrong token cannot open the gate. A release retry for the _same_ token may be idempotent only after acknowledgment, not globally. Fallback leases cannot be consumed by update/uninstall. `confirm-uninstall` validates under the captured generation before acknowledging background stop; any intervening generation switch rejects. Read-only prepare is advisory, not admission.

During an update decision window candidate and rollback Core must start fenced _before_ opening any ingress, including reconciliation and independent native workers/timers. Core `ready` while held is internal only: Supervisor continues to report `starting` until commit and the exact generation's boot lease release ACK; only then does it report `ready` and allow writes. Requires services-owned boot-held API at `@zcode/services/node` (MAIN approved `CoreAuthorityOptions.admissionFence` and `CoreAuthorityResult.bootAdmissionLease`, interface request in `.tmp/interface-handoff.md`). CLI adopts the actual factory lease into the existing CoreMaintenanceAdmission token owner; it does not acquire a second late freeze. Missing public factory boot hold fails candidate readiness closed. A two-archive locally validated update may use a test-only launcher declaration restricted to the exact current-checkout source-paired CLI artifacts and must distinguish this from the production default launcher, which must never advertise that capability for arbitrary old release metadata. A source-paired CLI held-boot smoke may request native boot capability only after its actual bundled CLI is rebuilt in this checkout and the initial constructor/claimBoot executable contract is checked; its verified exact lease, pre-open refusal and post-release fresh census are evidence of that one artifact, not proof an arbitrary old installed release is safe. Old/unattested releases require a separate pre-effect compatibility gate before a production Supervisor update can launch them held. Boot compatibility selection is an installer-owned, strictly typed LOCAL SOURCE ONLY record outside the untrusted archive, bound to the specific expected archive/target/version/release ID and installed Core/CLI/Agent/Node/component/tree digests plus executed source recipe; archive metadata and caller environment alone are never capability evidence. Both pending and previous current must validate before freeze/stop/pointer mutation; recheck selected bytes before held candidate and rollback spawn, reject arbitrary command overrides, and derive boot flag only from this verified selection. Online downloaded/legacy releases lacking an established trusted publisher selection fail closed rather than running an old executable to discover support; constructor-held CLI claim remains mandatory and neither local record nor claim proves all preconstructor autonomous paths. Until the services seam is implemented and tested, candidate rollback certification remains blocked. Stable local path fallback remains for no pending release. Release fixtures remain isolated, no external downloads or user service registration.

Real-process qualification (source-derived, not fake-Core certification): run a pre-import isolated public `@zcode/services/node` factory probe that returns sanitized pre-freeze/freeze/post-freeze native and external activity and a structured failure stage, without logging profile or credentials. A missing idle lease must have a source-backed cause before any maintenance assertion changes. Only the launcher-selected source-bundled Agent command may request strict storage-startup handshake via `ZCODE_AGENT_SERVER_REQUIRES_STORAGE_STARTUP=1`; caller-specified command must not be upgraded into trusted release provenance. This flag is a request for a real validated startup receipt, not a capability certificate or bypass of Core DB identity validation. Release staging must reject bundles referencing an unresolved bare `sqlite` package; ESM server-core bundle must supply a Node-local require for bundled CJS dependencies' `require('fs')` (without giving renderer/remote input a module-loader capability); `node:sqlite` must remain Node's built-in specifier after bundling (tsup's default removeNodeProtocol rewrote it into an unexecutable Core). Bundle dependency scanning must recognize `createRequire(import.meta.url)`-bound generated `require2('node-pty/lib/utils')` and esbuild `__require` aliases as actual package references even with the ESM bundle's local `const require = createRequire(...)` banner (an analysis-only shadow must not hide packages), without treating unrelated shadowed `requireN` functions as Node loaders, and distinguish generated `from "pkg"` imports from plain data strings such as `"from", ", "` in embedded SDK tables; never silently omit a genuinely referenced package. This scanner consumes only this checkout's esbuild-generated entry artifacts; nonliteral runtime module lookup is not certified by static parsing and needs executable release evidence. Real-process qualification launches installed binaries from disposable cwd/HOME/XDG/TMPDIR, with explicit Node old-space cap, no inherited NODE_OPTIONS preloads, loaders or checkout-dependent PATH; preserve shared heavy-slot ownership and one-child internal-concurrency controls. If an installed Agent closes stdout under this environment, inspect its bounded stderr/exit from the selected installed Node+Agent bytes before changing the runtime or allowing any extra executable path. Only a verified runtime dependency may be added to the isolated installed PATH; never restore parent PATH or loader. The Agent's IPC socket is created below TMPDIR; on macOS its full UNIX pathname must fit the OS limit, so use a short, exclusively owned disposable /tmp profile rather than the longer per-user tmpdir path (no fallback to a shared user profile). The diagnostic child must close and be reaped before the profile is removed. A benign synthetic parent preload/PATH sentinel must fail to execute in installed children. Any relative release path on Windows resolving to a different drive is outside the installed releases root and must be refused, not trusted. Install two disposable releases via actual ReleaseInstaller archive validation (manifest target/version, runtime files and archive SHA), using source-built Core/CLI/Node artifacts with explicit provenance; a directory containing only a manifest is not executable release evidence. Launch those consumed artifacts through the production launcher selection. Verify a first installed Core directly, through the real Supervisor control socket, and through the installed `server-cli.js serve --supervisor` entry (which selects the default production launcher): open from ReleaseManager.current, fresh maintenance census and exact release, then stop/reap child and close socket/release lock in order. The installed CLI must latch the Supervisor's READY transition synchronously before it becomes externally observable, and register foreground completion before Supervisor starts: a fast control-stop between READY and the CLI await must still return success and exit after child/lock teardown, never wait for a missed status poll or misreport startup timeout. Test actual OS old child termination/close, held candidate readied before commit, exact open ACK after commit, previous held rollback on pre-open failure, and loss of actual Core open ACK preserving child/pointer/lock. Real accepted native/Host running, waiting, and unknown facts are required for nonforce refusal; injected constant activity is insufficient. Bounded cleanup must target only owned children/groups and never treat PID-only stale lock as recovered. Missing services pre-init native fence prevents a PASS even when candidate IPC claims held-ready.

Rollback-open lost-ACK acceptance: after a REAL candidate fails before READY and the failed child is reaped, Supervisor restores the previous pointer and launches the previous installed release HELD. A transport observer may suppress only the matching actual previous Core's outbound boot-release ACK after the effect, recording its request/lease ID. The old current Core is terminal; rollback Core remains live, lock active, previous pointer current, transaction closed, state stop-failed. A fresh maintenance-begin/release directly against that same rollback child must succeed (underlying admission actually open); ordinary apply-update must not launch a third child, and only explicit fixture cleanup may stop it. Separate pre-open rollback failure terminates a definitely held child and cannot be called possibly-open. State owners: Core controls accepted input and exact boot lease; Supervisor controls generation/lock/pointer; observer alters delivery only, never Core business activity. Order: failed candidate close → restore pointer → previous HELD ready → commit restore → exact release EFFECT → ACK suppressed → uncertain stop-failed, no automatic restart. This fixture's identical-byte synthetic local archives are not production provenance or cross-version compatibility.

Real accepted-activity refusal: the refusal fixture must send a real command through the selected installed Agent/Host admission path and observe its actual accepted receipt and source-owned lifecycle/activity fact. Cover a running accepted turn, a waiting approval/question, and a genuinely uncertain accepted owner/run after a bounded transport/process fault; do not inject a constant census, fabricate heartbeat counters, or use a fixture flag as the authority. For every case, ordinary non-force apply-update must be rejected before candidate launch, old-Core stop, or current/pending/transaction mutation; assert the same Core PID/generation and exact leases/owner remain protected, and clean up only the accepted fixture input and its owned processes after proof. The admission owner remains Core/CommandInbox or Host respectively; Supervisor obtains a fresh Core-owned census only after admission is frozen. Event order: accepted command → source-owned activity/uncertainty → update freeze/census → non-force refusal → exact lease release → same old owner remains ready. A stale activity snapshot is not a substitute for the post-freeze census.

Acceptance: controlled barriers at maintenance request/reply, pointer-read await and release; replacement death before/after lease; late ready/heartbeat/activity/terminal/restart; busy/waiting/unknown refusal; candidate failure/ready timeout and rollback; failed kill/reap; real subprocess Core and verified-format local releases. Lock survives unconfirmed terminal. A dead Supervisor PID by itself never authorizes automatic reclamation of a leftover lock: an orphan Core or its descendants may still own the profile. Stale/invalid locks require explicit operator verification of the Core process tree and separate recovery; shutdown/uninstall checks must not treat stale as released. Fresh lock acquisition and owner-token release remain atomic. Cross-owner native autonomous ingress is a separate FULL_CORE proof, not implied by RPC read lock. Desktop continuous and mobile replayable transports attach to one Core owner but retain their own delivery semantics; neither owns update.
