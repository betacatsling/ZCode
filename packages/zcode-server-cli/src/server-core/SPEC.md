# Persistent Core authority (core-boot)

Core is the sole process-level owner of the local service collection and its persistent profile/target catalog; each window attaches over a scoped transport and disconnecting a window does not stop Core. The installation marker under `ZCODE_SERVER_ROOT` supplies the stable target identity. The profile/target root is selected by the services composition in Core, not by an individual window.

Boot sequence: validate installation identity -> construct collection with native source ports and maintenance coordinator via the public `createCoreAuthority({installationId,profileRoot,zcodeBuiltinProviderConfigFilePath})` Node composition port -> reconcile pending target receipts/archive policy before enabling _new_ admission -> expose RPC -> send ready to Supervisor. `CoreAuthority` owns the single ServiceCollection and maintenance port; its required `dispose()` closes both the collection resources and the persistent Catalog/Target writer exactly once; its `reconcileBeforeAdmission()` opens new admission only on confirmed success. Read/history/diagnostics remain available if reconciliation is uncertain; Core may advertise ready for those reads while new admission remains fenced. Boot failure must close partially constructed resources and must never send ready. Missing composition export or native fence/activity source fails closed, never silently falls back to a standalone writer or inferred idle.

Maintenance sequence: Supervisor IPC begin -> freeze native and external new admission with one owned lease -> drain in-flight admission -> read fresh native and external activity -> reply with `nativeActivity` and `externalActivity` under the validated IPC schema; if unsafe reject and release the same lease; otherwise hold until update/uninstall/fallback Core stop (or explicit release on failure). Concurrent maintenance operations must not overlap while one freeze is in flight or a fallback lease is held. Failure to stop Core must attempt to release only the owned lease; a release failure remains unsafe, never a successful uninstall. Client detach never releases the fence; stale release fails closed. Release of an already successfully released exact token is idempotent (including an ACK-loss retry), but an unknown/different token never releases the current lease; a failed underlying release does not mark its token released. Keep only the last completed token; new adoption/acquire invalidates the previous completion. Shutdown may retry an in-flight release and must not treat an uncertain release as permission for replacement. Explicit operator stop is separate and always allowed. On shutdown release service resources and close transport. Desktop continuous and mobile replayable connections share Core owner but not delivery semantics.

The real Core RPC attachment must expose its already registered Catalog and hierarchy descriptors through the public client and window-scoped mount; the renderer must not manufacture a replacement Catalog or native index. Generic loopback `/ws` has no Host ticket: it must not expose Catalog mutations/reads, hierarchy create/owner facts or Host commands/history. Only one-use `/ws/host` may expose these descriptors; never broaden profile availability for a browser test. A fixture may import an isolated Git repository via the real Catalog command; it must not substitute an empty authority for that test. Native create remains disabled until independently owned durable receipt/mapping exists.

Acceptance: a real subprocess Core/Supervisor control roundtrip can detach a client without killing Core, reject maintenance racing an accepted command, retain fence through lifecycle stop, permit explicit stop, and reject a stale token. No packaged-release claim without its own smoke test.

Authority closure: Supervisor owns only lifecycle MAINTENANCE state, never a second task queue. The replacement Core MUST remain fenced through the whole update/rollback generation until Supervisor verifies it is the intended generation; old lease is not releasable after its owner has exited. Held boot passes `CoreAuthorityOptions.admissionFence: "held"`; Core must adopt only the pre-initialization factory `bootAdmissionLease` into its existing maintenance owner, never acquire a second late freeze. A missing factory lease aborts readiness; reconcile must not open writes before Supervisor commits and acknowledges release. Lost acknowledgment after commit preserves candidate/lock/pointer as stop-failed, never unilaterally rolls back potentially accepted work. A lost lease or uncertain replacement blocks new mutations, while read/history remain recoverable. Explicit stop is not automatic maintenance. IPC carries only token/epoch and serializable activity; no release closures cross process boundaries.

Factory integration: the public `@zcode/services/node.createCoreAuthority` is the only production Core composition. `ZCODE_SERVER_ROOT` is the installation/runtime directory, NOT the profile writer identity. The actual data/config root remains `getAppConfigDir()` (including `ZCODE_DATA_BASE_DIR`); the profile lock must cover that same root, not merely the installation directory. The factory mounts a real scoped Target/Catalog/Host, Registry, and native directory derived from configured native CLI paths; missing native DB is unknown historical state, not an empty certified source. CLI CommandInbox alone owns native durable IDs/receipts. Each Core process owns one profile writer and one process-wide native-worker census/freeze; no worker spawn or timer mutation may bypass that fence. Acquire gate before worker census, drain already admitted operations, verify each same-worker epoch and live counts before any idle claim. A cached frozen activity snapshot is valid only while exactly the same resident client objects remain owned/alive; worker exit, replacement or unresolved start must invalidate it, including the IPC read after the lease is issued. Dispose of children, subscriptions, repositories and writer lock after either successful or partial startup (including CLI storage startup failure after real ServiceCollection composition); a failed reconciliation retains history reads but never enables new admission. Partial composition failure _inside_ `createLocalServices` before a collection is returned must also release any already allocated resources; merely releasing Core's outer file lock does not satisfy this. Reconnect queries the same owner and command ID. Tests import the public export directly before exercising default Core subprocess without a factory override.

Event order: installation identity -> resolve actual profile/config/native roots -> acquire profile lock -> construct real service collection (admission closed) -> initialize Target/Catalog and native facts without query-side migration -> reconcile receipts/archive policy -> open new admission only if confirmed -> ready/read RPC -> shutdown fences and disposes once. Native create: verified target/generation -> V4 CLI CommandInbox create(commandId) -> durable CLI original-ID receipt -> sidecar mapping -> directory read; duplicate ID queries receipt rather than allocating again. Old Core lease cannot fence a replacement generation; Supervisor replacement handshake remains a separate requirement, so automatic update/release is not certified until that hook exists.

Fresh-profile Core boot must explicitly prepare both the task-index through its migration writer and the configured CLI session DB through the CLI-owned storage startup _before_ serving sidebar reads. Initialization is a boot mutation under the profile writer, never a read fallback. If either preparation fails, reject readiness or expose recoverable reads only if the native source was already valid; never label an absent DB as empty historical state. When Core is shut down, stop any startup worker before releasing the lock. A cross-root configured native DB cannot silently share the profile lock with another writer. Regression must exercise the public factory with an actual sidebar snapshot on a fresh isolated profile, rather than only revision/read-error checks.

Implementation status: the public production factory and default Core caller are mounted, with a real process-wide three-lane worker census and live CLI freeze on resident workers. `certifiedCreate` remains false: CLI draft-create (`createSession` without `firstInput`) has no durable global query fact after worker restart, and production has no reviewed sidecar mapping writer for new native receipts. A fresh profile is initialized by the real Core task-index migration writer and configured CLI storage-startup worker before a full sidebar read; failure aborts readiness instead of fabricating an empty native history. The Core subprocess test covers fresh sidebar, resident CLI freeze and stale-worker activity rejection, post-composition CLI startup failure and reacquisition, duplicate lock/reconnect/stop/restart. Reconciliation-fault and pre-collection constructor cleanup still lack proof. None of those tests certifies a live native create or worker-restart receipt recovery.
