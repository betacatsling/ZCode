# Persistent Core authority (core-boot)

Core is the sole process-level owner of the local service collection and its persistent profile/target catalog; each window attaches over a scoped transport and disconnecting a window does not stop Core. The installation marker under `ZCODE_SERVER_ROOT` supplies the stable target identity. The profile/target root is selected by the services composition in Core, not by an individual window.

Boot sequence: validate installation identity -> construct collection with native source ports and maintenance coordinator via the public `createCoreAuthority({installationId,profileRoot,zcodeBuiltinProviderConfigFilePath})` Node composition port -> reconcile pending target receipts/archive policy before enabling _new_ admission -> expose RPC -> send ready to Supervisor. `CoreAuthority` owns the single ServiceCollection and maintenance port; its required `dispose()` closes both the collection resources and the persistent Catalog/Target writer exactly once; its `reconcileBeforeAdmission()` opens new admission only on confirmed success. Read/history/diagnostics remain available if reconciliation is uncertain; Core may advertise ready for those reads while new admission remains fenced. Boot failure must close partially constructed resources and must never send ready. Missing composition export or native fence/activity source fails closed, never silently falls back to a standalone writer or inferred idle.

Maintenance sequence: Supervisor IPC begin -> freeze native and external new admission with one owned lease -> drain in-flight admission -> read fresh native and external activity -> reply with `nativeActivity` and `externalActivity` under the validated IPC schema; if unsafe reject and release the same lease; otherwise hold until update/uninstall/fallback Core stop (or explicit release on failure). Concurrent maintenance operations must not overlap while one freeze is in flight or a fallback lease is held. Failure to stop Core must attempt to release only the owned lease; a release failure remains unsafe, never a successful uninstall. Client detach never releases the fence; stale release fails closed. Explicit operator stop is separate and always allowed. On shutdown release service resources and close transport. Desktop continuous and mobile replayable connections share Core owner but not delivery semantics.

Acceptance: a real subprocess Core/Supervisor control roundtrip can detach a client without killing Core, reject maintenance racing an accepted command, retain fence through lifecycle stop, permit explicit stop, and reject a stale token. No packaged-release claim without its own smoke test.

Authority closure: Supervisor owns only lifecycle MAINTENANCE state, never a second task queue. The replacement Core MUST remain fenced through the whole update/rollback generation until Supervisor verifies it is the intended generation; old lease is not releasable after its owner has exited. A lost lease or uncertain replacement blocks new mutations, while read/history remain recoverable. Explicit stop is not automatic maintenance. IPC carries only token/epoch and serializable activity; no release closures cross process boundaries.

Factory integration: the public `@zcode/services/node.createCoreAuthority` is the only production Core composition. `ZCODE_SERVER_ROOT` is the installation/runtime directory, NOT the profile writer identity. The actual data/config root remains `getAppConfigDir()` (including `ZCODE_DATA_BASE_DIR`); the profile lock must cover that same root, not merely the installation directory. The factory mounts a real scoped Target/Catalog/Host, Registry, and native directory derived from configured native CLI paths; missing native DB is unknown historical state, not an empty certified source. CLI CommandInbox alone owns native durable IDs/receipts. Each Core process owns one profile writer and one process-wide native-worker census/freeze; no worker spawn or timer mutation may bypass that fence. Acquire gate before worker census, drain already admitted operations, verify each same-worker epoch and live counts before any idle claim. Dispose of children, subscriptions, repositories and writer lock after either successful or partial startup; a failed reconciliation retains history reads but never enables new admission. Reconnect queries the same owner and command ID.
