# Workspace hierarchy service

Profile Catalog owns project/binding/workspace display state and the persistent agent index; TargetWorktreeService owns Git, generation and admission; native session storage owns native IDs and runtime truth; Host owns external specs, commands and events. Hierarchy is a read/command composition only, never an allocator for native IDs or a second queue. Unknown IDs must fail closed; feature-off native transport remains unchanged.

Client submits workspace ID, harness ID, model binding, relative cwd and stable command ID. Hierarchy reads the authoritative workspace/binding/manifest, derives v2 spec, target verifies generation/cwd under admission, Host durably records creation before adapter effect. Same command ID retry queries original receipt; different intent with same ID rejects. Native creation uses the existing native V4 creation path with its original allocator, not Host. Navigation returns original native session ID and scope, or stored external spec/history-only. Resolve path+identity+remoteSessionId only within the authenticated target scope; no path-only remote ownership.

Activity: native + external accepted/waiting/running/uncertain must be aggregated before removal or maintenance. Automatic maintenance uses a serializable lease (token + epoch): reserve workspace admission synchronously, obtain the real native CLI inbox fence, drain already accepted workspace admissions, then read fresh activity; only zero, finite, online facts permit issuance. Hold both fences until the authorized Supervisor operation ends and the matching lease is released. Two concurrent freezes do not share a lease; stale, mismatched, or duplicate releases fail closed. If native fencing is ambiguous or its release fails, keep workspace admission frozen (operator intervention required); failed activity checks with a valid native fence release exactly that fence. The Node adapter for the real native control port must check its issued CLI lease after the workspace drain and before the fresh combined activity read; native UUID epoch/frozen/unknown changes poison workspace admission (distinct from the Core maintenance lease's monotonically increasing numeric epoch) instead of treating a dead/replaced worker as idle. A confirmed busy native snapshot may release its exact lease; a rejected/ambiguous release must never reopen workspace admission. Legacy callback-only fences are a composition seam, not production proof: service-boot must inject a verifiable fence for automatic maintenance. The target maintenance gate, if required, must be acquired before this workspace gate, never by acquiring target exclusive from inside a workspace admission. Explicit operator stop is separate and does not require an idle lease. A disabled new-admission flag does not stop running sessions. The Core owns the lease across authenticated IPC, not the Supervisor; if Core dies, do not treat silence as idle or reuse a prior token. RPC carries only JSON-safe request/lease values, never an action closure or native release callback. Target-local callbacks remain in Node and are never serialized over RPC.

Event order: client intent → catalog/target owner check → target admission → Host create-command reservation → adapter activation → Host journal/event → hierarchy projection. Desktop continuous and mobile replayable consume the same durable owner; reconnect queries command/receipts rather than resending prompts. Stale target generation, epoch or ambiguous native mapping blocks mutation. Tests: two targets same path, unknown ID, command retry/conflict, native original scope, inactive external history, accepted-before-running removal/maintenance, offline target, concurrent creation and removal.

Composition registers both catalog and hierarchy RPC descriptors alongside AgentHost for local and remote server services. Native index/owner, native activity and freeze callbacks must come from the live V4 owner; absent inputs fail closed for catalog reads, native navigation, removal and automatic maintenance. Remote identity builder and authenticated attachment registry must be supplied by the remote runtime. A window-only local Host cannot claim to be the process-wide profile owner; the persistent Core/attachment owner must mount the singleton and connect remote service collection. The external Host index uses durable manifests/read models; unresolved creation receipts without manifests block removal/maintenance but are not yet represented as sidebar rows. Do not label this as full profile recovery or native activity certification until those dependencies mount.

Native production facts: the persistent Core injects an already-configured absolute task-index path plus the same launch cwd/env/config inputs as the native CLI, a verified migration sidecar mapping reader and an attached live V4 runtime port. The bridge's configured factory delegates session DB selection to the CLI's exported configured-path resolver (including relative-to-cwd configuration); the low-level absolute-path factory is for callers that already received the resolved path from that resolver. A read validates both SQLite sources read-only even with no sidecar mappings, never invokes CLI startup or creates a fallback database. A sidebar row is admitted only when its task-index `(workspace_key, workspace_path, task_id)` exactly matches the mapped source scope AND the session store's explicit `workspaceID` attests the same native scope. A missing workspaceID is migration evidence, not a trustworthy live navigation owner: leave the row pending/read-only instead of inferring ownership from cwd containment/equality. Preserve mapping's original native ID, cwd subdirectory, source scope, target and worktree generation. The mapped target/generation must be checked by the hierarchy's current target authority before new mutation; a stale path cannot grant execution. Persisted task status does not certify idle/running activity. Live counts and admission fencing come from the attached V4 owner, not SQLite. Resolution order: mapped scope + two current read-only facts → tree/original owner lookup → current target check → mutation through V4; missing or ambiguous facts fail closed. Desktop continuous and mobile replayable are projections of the same owner, not extra native runtimes.

## Hierarchy actions / recovery boundary

Target owns live removal facts and the frozen removal recheck; hierarchy exposes a server-resolved preview by workspace ID + expected generation, never accepts client Git/activity assertions. A stale/missing workspace or foreign target cannot preview or remove. UI only allows confirmation when `safe` and no unknown facts; it displays each Git and activity risk and warns that external processes may race after preview. Confirmation calls the existing catalog remove, which independently freezes and rechecks. A rejected remove stays open.

An external v2 session is writable only when the current target, project, workspace, generation, identity and path match its original spec. The generation is the target's instance marker, not a path label. Native source facts must carry original generation and repository binding ID to prove the same instance; missing legacy facts return history-only, preserving original native ID and scope but never rebinding to a new worktree. Catalog/binding/target own the authoritative state; navigation never allocates or repairs workspaces.

Recovery for missing Target receipts is an explicit read-only unresolved operator query, not a same-path adoption or Git retry. Its typed action is `inspect` (no mutation). Future receipt-backed recovery requires an authoritative target proof and deliberate operator command; no auto-adopt. Event order: client ID/generation -> catalog target resolution -> target preflight/activity -> preview -> user confirmation -> catalog remove -> target frozen fresh recheck -> result. Stale result always fails closed. Desktop and mobile read the same target facts; preview never counts as a lease or a durable removal authorization.

Acceptance: rebuilt same path with new generation and old external/native session yields history-only; unknown native provenance is history-only. Preview reports main/dirty/untracked/submodules/locks/activity/unknown distinctly; unsafe/unknown/main disables confirmation, rejected removal retains dialog and risk warning. Pending-recovery inspection never triggers target mutation.

Only `standalone-server` with an explicit target ID mounts the writable profile Catalog/Target/Host. A window-scoped `desktop-local` collection must use a Core RPC attachment, never open the profile writer itself. Core is the single writer for catalog and target facts; a window may only read/command through Core. Required native index/owner/activity/fence are injected from the _live_ native production bridge; missing facts fail closed, not an empty index or idle activity. A local identity fallback is valid only for a local target; remote targets require a trusted builder.

Boot ordering: open Target → open Catalog → reconcile pending operations and archive policies against durable target receipts → enable NEW native/external admission. Reads/history and receipt diagnostics are available while reconciliation is pending or uncertain. Reconciliation failure must leave admission closed and must not retry Git effects. Fencing maintenance additionally blocks new admission before reading fresh native and Host activity; accepted controls/history are not new admissions. Disposal closes the single profile owner and stops any further async initialization. Repeated requests use their original command receipt, not path/branch similarity. Desktop live and mobile replay both query the same durable Core owner, with independent delivery semantics. Boot tests exercise the production factory with an isolated root, including missing-facts and unreconciled failure. The Core process must explicitly await its composition `ready()` before advertising admission; obtaining a service descriptor alone is not boot completion. `ready()` is single-flight, and a failed reconciliation retains the first failure without re-running Git or reopening the profile. A dispose racing asynchronous open/reconciliation prevents all subsequent admission; the profile writer must close exactly once after the in-flight open settles. Reads and history do not wait for reconciliation. A failed reconciliation must not strand accepted-turn controls (Host owns their immutable receipt/epoch fence).

Native bridge is a required typed input of the standalone Core composition (configured-path complete SQLite index, trusted native owner, live V4 activity and native CLI fence). It is _not_ a user-settable startup path; Core owns the stable root separately. Unsupported Codex/Claude/ACP must not be registered as executable adapters until capability proof; Pi is registered through the existing Host factory. Local on macOS/Windows may use path fallback for identity; an SSH/Linux target requires an authenticated identity builder. No window opens a second profile writer.

```text
Core writer: Target receipt + Catalog intent -> reconcilePending -> reconcileArchivePolicies -> ready
                                         ├─ reads/history accessible while pending/failed
                                         └─ NEW Host/native admission enabled only at ready
window attachment -> Core RPC -> same Host owner (desktop continuous / mobile replayable)
```

## Authority-product owned closure (pending implementation)

Core owns one collection and Target/Catalog writer; configured native index is read-only, native CLI owns live session admission. Catalog/Host mutations must first cross the same Core maintenance gate. Core boot waits for receipt/archive reconciliation; an unknown receipt blocks *new* admission, never replays Git. The native owner cannot be inferred idle from persisted SQLite. Session list options are derived from the live target Registry and certified harness capabilities, scoped by target/workspace/generation; unsupported routes never appear. Native original IDs and reviewed mapping provenance are preserved, unknown provenance is history-only.

```text
Supervisor begin(token/epoch) -> Core maintenance gate closes Catalog+Host admissions
  -> existing native CLI worker fence -> drain old admissions -> verify same worker lease
  -> fresh native+external activity -> Supervisor stops old Core -> apply/rollback
  -> replacement Core starts FENCED -> verify operation/generation -> open admission
old Core fence cannot be released until owner disposed; loss/unknown remains blocked.
Operator stop is distinct and may stop busy sessions deliberately. Desktop continuous and mobile replayable read the same Core owner, never issue a second accepted command on reconnect.
```

Acceptance: concurrent write/freeze, lazy Host close versus delayed registry startup, reviewed Git admin instance swap, Core subprocess concurrent startup, unknown native worker fails closed, stale release never thaws, actual target/catalog lifecycle in disposable profile, and sidebar reads do not launch workers.

Implementation status: `listCreateOptions` currently exposes only Registry-certified Pi host-managed selections. The native V4 creation receipt and process-wide native maintenance owner remain unmounted; an injected bridge is not itself a Core production boot. Never claim `createCoreAuthority` works until Node exports a factory backed by real configured paths and Supervisor closes the replacement generation gap. Synthetic native fixtures in unit tests do not certify production native execution.

New native create is fail-closed unless its injected live owner explicitly certifies a durable creation receipt; its harness catalog entry stays `unknown` without that attestation. Existing native history lookup retains the original ID even when new creation is unavailable. This does not affect the feature-off native route. The target-exclusive native create admission holds the verified generation/cwd until V4 returns. An unmounted `NativeRuntimeFactsPort` is *not* certified by a controlled test flag.

Operator recovery inspection reads current Target receipt/pending intent under Target owner instead of always claiming receipts unavailable. It returns confirmed receipt facts only after Target validates the instance; pending/uncertain remains unresolved and inspect-only. No automatic adoption, retry of Git, or Catalog-local reconstruction is allowed. An ID absent from both Catalog and Target is unknown, not a recoverable workspace.

Native bridge's maintenance interface requires a verifiable same-worker lease (`verify` + `release`); the old release-only callback is not a production port. Controlled test fixtures may return a verified lease, never stand in for global process enumeration or a real CLI epoch.

Core native boot admission (opt-in, disabled by default): the Core owns the initial hold before any asynchronous initialization; the Node spawn gate allows only its first storage worker. The paired CLI constructor synchronously freezes its existing CommandInbox before resident callbacks or any protocol command. A configured custom CLI is refused **before spawn** unless its trusted deployment declares both storage startup and constructor-held fence capability; a declaration is not proof and Core must claim the exact live worker/lease. After storage readiness and Catalog/Target reconciliation, Core exposes a one-shot `bootAdmissionLease.release()` that checks the same CLI epoch/frozen activity and releases the CLI lease before reopening workspace admission. Ordinary maintenance is a distinct lease; its verification can reuse the held boot fence, and its release cannot clear the initial hold. Wrong worker, busy/unknown status, lost release acknowledgement or concurrent maintenance fails closed. Production native creation stays disabled; Desktop's authenticated registry and Supervisor's generation/rollback handoff remain separate requirements. Tests require constructor-held denial and claim, prelaunch refusal, same-worker release, nested maintenance, worker rotation and real DB/Target lifecycle; an in-memory fixture alone is not full acceptance.
